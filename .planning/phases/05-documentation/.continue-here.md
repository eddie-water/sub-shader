## How we are working — preserve this on resume

### Authoring voice rules
- **User authors all final prose. Claude scaffolds, suggests, never writes final copy.** All bullets are the user's voice (restored from outline).
- **Build upon previous framings, don't restate.** Each section/subsection should pick up where the previous left off without overlapping its content. New section = new teaching beat, not a rephrasing of the prior beat.
- **Avoid layered forward-pointers.** A subsection introducing a forward-pointer inside another forward-pointer (e.g., §2.2's audio-bridge nest pre-empting §3) creates noise — push generalizations to where they're actually unpacked.

### Edit pacing rules
- **Propose, don't change.** Don't apply edits without running them by the user first. Show candidates, wait for explicit pick, then apply.
- **One change at a time.** Even small wordsmith fixes get proposed before being applied.

### Delivery rules
- **Be concise.** No long preambles, no enumerated meta-summaries, no defensive explanations. Tight bullets/tables.
- **Plain English.** When the user asks "does this make sense?" or "how does this flow?", answer in plain English. Don't lecture about plan must_haves unless asked.
- **Granularity matches the question.** Ready to discuss: one bullet, one subsection, one section, or whole-doc flow. Match the level of zoom the user is asking about.
- **Don't surface side-concerns.** Branch state, dirty trees, untracked dirs, repo hygiene — none of that during authoring sessions. Authoring momentum is the priority.

### Specific patterns the user values
- **Heading-suffix breadcrumbs** (§2.1 The Goal → §2.2 The Tool → §2.3 The Basic Case → §2.4 The Geometric Interpretation) are working well as a narrative spine.
- **Bold parallel sub-headings** inside one subsection (e.g., **2D** / **3D** / **ND** in §2.4.3) preserve all original bullets while removing artificial subsection breaks.
- **Cross-section signpost bullets** (a closer that names what the next section will pick up) are the way to make the "build upon, don't overlap" rule visible.
